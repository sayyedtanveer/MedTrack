Each stock endpoint owns its transaction and the inspected inventory helpers flush rather than commit. An uncaught exception before the route commit should roll back the session's mutations. Several logical failures currently take the successful commit path. Rollback under injected failures and locking across concurrent PostgreSQL sessions remain validation work for the repair.

## Confirmed defects and proposed minimum corrections

1. **Duplicate and excess output.** The same partial receipt was accepted twice in an isolated handler probe. A subsequent receipt posted six against an order for five. Issue and return also lack a durable retry key or replay check, and batch uniqueness only identifies a batch. Use an explicit client-generated operation UUID per logical submit, reused on retry and distinct for a second partial. Check a canonical payload fingerprint and replay the original response under the order lock. Return conflict on a changed payload. Cache-only or fail-open audit deduplication is unsuitable for stock. The orchestration audit pattern at workflow_orchestration_service.py:1605 is not a transactional stock identity. Recommend approval for a dedicated, constrained operation record keyed on tenant/order/action/key, same transaction as postings, with fingerprint and original response. Assess reusing a same-transaction audit writer only if durable uniqueness, payload and original response can all be proven. Existing audit rows must not be repurposed or rewritten.
2. **Return can create inventory.** In the isolated handler probe, a return of three credited the warehouse three and reduced the vendor bucket by only one. At supply_chain.py:2638–2708 the source may be absent or clamped to zero. Check both the order's outstanding balance and the vendor location's availability before posting. Use the existing strict bucket move with equal debit and credit. Validate the batch attribution and refuse excess instead of clamping. Derive non-BOM issue balance from approved, order-scoped issues and related ledger movements. Preserve manual orders.
3. **Receipt can consume less than its snapshot or draw from other orders.** InventoryService.consume_subcontract_raw_materials reads shared vendor stock by material/location. It does not cap by the receiving order's issued-minus-consumed-minus-returned balance. A real service probe with mocked storage confirmed that a 0.25 shortage was accepted and only the available remainder was logged. Check all order-specific and physical balances before committing output. Reject the receipt transaction on insufficient issued material or stock. Different orders sharing one supplier need separate attributable balances. Record selected lot movements and validated allocation separately from untracked quantity. Existing issue schema identifies the issued lot but does not persist a per-issue consumption balance; design traceable allocation before claiming lot-level completeness.
4. **Order state and balances can race.** supply_chain.py approval, issue, receipt, return and cancel read the order without FOR UPDATE. Stock row locks do not serialize the order's limits or status. Lock the same tenant-scoped, nondeleted order before checking transitions/idempotency. Then acquire supplier/location setup locks if needed and material, batch and bucket locks consistently in a documented order. Current consume path takes a bucket before locking its material, whereas issue and return lock material first; standardize to avoid deadlock. Validate source and destination locations by tenant, active/deleted and appropriate type, and verify batch material/identity. Enforce positive quantities in DTOs before touching stock and validate precision against the persisted scale. Test concurrent operations across two real sessions before release.
5. **Snapshot and output mapping.** supply_chain.py:2271 and :2408 do not enforce supplier tenancy, active BOM, exact product variant/material link or quantity UOM. Receipt trusts the supplied material ID. Picker :2130 uses explicit variant links, then code fallback; it skips deleted variants but does not require active variants and can return inherited template candidates. Approval snapshots only direct material lines and skips nested variant/template lines; scrap is applied to captured lines. Match an active, tenant-valid selected BOM to the intended output at approval and validate receipt material and UOM. Preserve approved requirements after BOM revisions. Reject or flag unsupported child structure for review rather than silently treating it as an empty recipe. Keep BOM-optional orders. Obtain a decision on historical code-only or mistyped product links before changing behavior for existing orders.
6. **Partial receipt rounding.** inventory_service.py:1813 multiplies each receipt by required/order quantity, then persists a three-decimal line counter. The example three receipts of one against order output three and requirement one yields 0.333 × 3 = 0.999 at the persisted scale. Preserve the proportional basis but post the difference between the newly rounded cumulative target and previously posted consumption. Reconcile scale across order lines, movement and bucket quantities. Final receipt reaches the approved snapshot exactly under the existing rounding policy; if the production quantity precision policy is ambiguous, obtain agreement before changing it. Actual scrap, lost yield and rejected output need separate definitions, so no inventory adjustments are inferred.
7. **Completion policy decision.** Recommend treating output fulfilled and materials reconciled as distinct conditions. A full receipt posts the authorized output and leaves any residual attributable stock visible and returnable. Transition to completed once every valid line reconciles to zero; older completed orders with open allocations need an exception view and authorized repair. Agree on the interim status and the allowed historical treatment before changing status semantics. Financial confirmation remains independent and does not gate production closure unless separately approved.

## Actual local PostgreSQL observations

The target was the previously identified local development tenant, under default_transaction_read_only. Existing constraints cover positive order/issue quantities, nonnegative stock buckets, bucket identity, batch identity and order number. They do not identify a logical issue/receipt/return operation or enforce an order's cumulative receipt/material limit. There is no unique per-order material snapshot key in this schema.

| Order | Ordered / received | Issued / consumed / returned / remaining per component | Recorded movements |
|---|---|---|---|
| SCO-20260929-0001 | 1 / 1, completed | Each of RM-MT-0002, RM-MT-0003 and RM-MT-0004 is 1 / 0 / 0 / 1. | Three issue transfers, one output receipt, no associated consumption or return. |
| SCO-20261001-0002 | 2 / 2, completed | Each of those three components is 2 / 2 / 0 / 0. | Three issue transfers, one output receipt and three consumption movements. |

The shared vendor buckets show one remaining unit for each of those three raw materials. This matches the recorded outstanding quantities for this sample but does not prove physical inventory. Issue records match the order line issue/return quantities for both samples. No negative line balance was observed in these two orders. Both historical orders say variant but their product IDs resolve to the semi-finished inventory material SF-MT-0001, and their output batches reference that same material. Both point to the same currently inactive BOM v3.0. Its present inactivity does not establish whether it was active at approval. The order snapshots remain present. Do not normalize old IDs, backfill consumption, or alter bucket balances based only on this evidence.
